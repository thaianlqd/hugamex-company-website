# Security review — local implementation

Reviewed 2026-10-05. This is a code review and local regression report, not a penetration-test certificate. Subsequent local Supabase/Gmail changes and actual checks are recorded in [SUPABASE_SMTP_REPORT](SUPABASE_SMTP_REPORT.md). Google OAuth, HTTPS proxy and production configuration remain untested.

## Findings fixed during implementation

- CSRF cookie/header mismatch corrected and verified with the real wire contract plus browser journeys.
- PostgreSQL metadata conversion corrected for publish/unpublish operations.
- Editor no longer sends read-only DTO fields back into the save request.
- Role combinations cannot bypass mandatory MFA; configured EDITOR MFA also enforced.
- Refresh/login/revoke race serialized with user locks; concurrent regression retains revocation.
- Private/referenced media checks retained, with tests for deletion and privacy transitions.
- React 19 title rendering and TipTap destroyed-instance lifecycle corrected through browser tests.
- Frontend tool dependency advisories addressed by removing Lighthouse from application dependencies. `npm audit` on the shipped frontend dependency tree returns zero findings at review time.

## Dependency review limits

Spring Boot was updated within the required 3.x family to 3.5.16. Its managed Security 6.5.11 addresses the SAML output issue; this app does not enable SAML. [Managed versions](https://docs.spring.io/spring-boot/3.5/appendix/dependency-versions/coordinates.html), [SAML advisory](https://spring.io/security/cve-2026-41003/).

Security 6.5.11 is still within the version range of the DPoP cache replay advisory. The application uses its own HS256 bearer/session filter, does not configure `DPoPProofJwtDecoderFactory`, and accepts no DPoP authentication flow. This is an applicability assessment, not a patched-dependency claim. A supported 3.x maintenance/security strategy must be reviewed before production; do not silently change the requested stack to Boot 4. [DPoP advisory](https://spring.io/security/cve-2026-41707/).

Lighthouse 10.1.1 is isolated under ignored `.tools/lighthouse`, not bundled or included in the frontend lockfile. Its tool-only dependency tree has audit advisories, including archive extraction/proxy dependencies. It was used only with already-installed Chromium and a fixed trusted localhost URL, without archive downloading or arbitrary targets. Review/update the measurement tool before using it on untrusted inputs. The isolation does not remove those tool advisories.

No exhaustive automated Java SCA/NVD scan, external penetration test, production header/TLS audit or recovery drill has been executed. No assertion of complete security is made.

RLS behavior follows [PostgreSQL 17 documentation](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) and [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security); production platform permissions still need verification.

## Phase 2 regression and preview seed

- HERO external URLs are kind-scoped, length-bounded, exact-host HTTPS only, with userinfo/nondefault ports rejected; image fallback is browser-side. No server-side remote fetch endpoint was added.
- The preview service job is dev-only, requires both ALLOW_SUPABASE_PREVIEW_SEED and RUN_SUPABASE_PREVIEW_SEED_JOB, validates the exact reviewed project and manifest fingerprint, uses existing service validation/audit, and exits. It never creates an authenticated HTTP session or marks an actor MFA-verified. Normal startup disables both flags. Production profile excludes the job. Access to the backend environment is already privileged server access; protect it accordingly.
- Stable keys/state and canonical fingerprints preserve owner-modified content/media, prevent duplicate entities, and check a zero-write repeat pass. No passwords, users, roles, TOTP, recovery codes, SMTP settings or applied migrations are changed by this content job.
- Atomic homepage reorder requires business RBAC/MFA and the exact set of existing UUIDs; regression includes MFA rejection and unchanged state after invalid membership.
- All 69 backend tests passed on Testcontainers. All five browser journeys passed on explicitly isolated Docker/file-mail servers; the ordinary E2E Supabase/SMTP refusal remains unchanged. CMS screenshots use the Docker fixture, not owner credentials, and mask user email cells.
- Read-only Supabase postflight verified 17 tables, four successful migrations, RLS and BYTEA. Pooler JDBC uses sslmode=require; an upstream pg_stat_ssl result was false. This does not certify end-to-end TLS or production runtime grants.
- No secret files are tracked or added to screenshots. Credentials and an MFA setup secret previously shared by the owner should be rotated/re-enrolled by the owner; this phase did not silently invalidate access.

The frontend image-host changes in the default API CSP do not certify static-host production CSP. Deployment, real Google OAuth, proxy/HTTPS headers, independent security assessment and dependency maintenance remain separate review items.

## Company-profile and account update

`PUT /account/profile` accepts only a validated display name and takes the target exclusively from the authenticated actor. Real PostgreSQL regressions reject anonymous/disabled access and id/email/roles/security-field injection, preserve other users and retain privileged MFA enforcement. No email/role/password/MFA change endpoint was added. Password change uses the existing service and revokes sessions; its UI is now a separate route with confirmation. Explicit logout uses the existing CSRF/cookie flow and clears auth/cache only after the API succeeds.

Company contact/fax updates reuse validated/audited settings services. Source content and archival of obsolete seeded previews are fingerprint guarded; owner changes are skipped. Historical 2022/2023 figures, customer references and old certification claims are labelled according to the supplied source. The phone popover is public-only, uses CMS values and makes no automatic external call.

Repeated browser QA temporarily reached the unchanged five-attempt/five-minute MFA limit. Tests were rerun after its normal expiry; the application limit was not removed or raised. Safe account screenshots mask email fields and exclude entered passwords, OTPs, MFA secrets and recovery codes.

## Public Maps follow-up

LocationMap constructs iframe URLs on fixed `https://www.google.com/maps`, encoding only CMS address text as a query parameter. It never renders raw iframe HTML or accepts a user-selected iframe host. Maps links use fixed Google search/direction paths; new tabs use noopener/noreferrer. Java does not fetch or proxy map URLs. Iframes are lazy, titled, referrer-policy=no-referrer, and keep a direct address link available. Deployment frontend CSP must explicitly permit the Google map frame origins; existing auth/RBAC/MFA, API validation and migrations remain unchanged.

## Content-only CMS and contact notifications — 2026-10-05

Homepage/section order, global settings and HERO management are denied backend-side for every CMS role, including SUPER_ADMIN. Developer presentation now lives in frontend code. Existing content CRUD keeps RBAC/MFA; new PRODUCT_CATEGORY is business-only and separated from editorial categories. V5 enables RLS on the relation table and revokes anon/authenticated access; public data still passes through Spring.

Contact notifications use a fixed server-configured recipient, fixed subject/from and a validated Reply-To. User content appears only in a plain-text body. Public CSRF, honeypot and rate limits remain enforced. The durable inbox/queue survives SMTP failure; attempts are bounded to five and provider exceptions/request bodies are not logged. SKIP LOCKED prevents concurrent workers processing the same due row; SMTP plus DB is at-least-once, not exactly-once. Notification metadata is visible only to business CMS. Old messages default to DISABLED, preventing retroactive sends. Tests use file transport or mocked SMTP. Real contact SMTP testing is explicitly requested by the owner for this follow-up.
