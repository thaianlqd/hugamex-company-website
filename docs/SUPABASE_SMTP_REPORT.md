# Supabase + Gmail SMTP integration — local dev

Scope: existing Spring backend, Supabase PostgreSQL Session Pooler and Gmail SMTP with `SPRING_PROFILES_ACTIVE=dev`. Google OAuth is unchanged and not configured/tested. No deployment, DNS change, production profile, business seed or QA-account copy.

## Implementation

- One source of truth: `app.mail-mode=${MAIL_MODE:file}`. Conditional providers ensure exactly one EmailService. File delivery is restricted to dev/test, including rejection when prod and dev are both active.
- SMTP works in dev/prod and validates host, username, App Password, sender and port. STARTTLS/auth/hostname checks are required; network timeouts and UTF-8 are explicit; mail debug is disabled.
- Both email-verification and password-reset messages describe purpose, OTP, five-minute expiry and a no-sharing warning. OTP hashing, purpose binding, single use, expiry, attempts, cooldown and rates are unchanged.
- Provider exceptions are replaced with a safe delivery exception. Auth challenge requests preserve the generic response on SMTP delivery failure so response status does not disclose whether an account exists; safe provider warnings remain available for diagnosis. Delivery is synchronous, so SMTP latency can still create a timing difference; this task does not introduce an asynchronous queue. Successful sends log only purpose and transport acceptance, never recipient, OTP, credentials or message body. Transport acceptance does not prove inbox delivery.
- Local env selects the requested pooler with SSL and Gmail SMTP. Existing security keys are retained. Env files remain ignored; no secrets are included in examples/docs.
- Read-only preflight/postflight script checks connection, table-name collisions, Flyway history, 17 core tables, RLS, BYTEA and owner count. QA helpers reject a Supabase target before reading fixture credentials or making HTTP requests. Playwright configuration refuses Supabase/live SMTP before running any journey.

## Migration review

V1 creates 17 application tables/indexes, constraints and BYTEA/JSONB columns. V2 adds four role names and seven empty homepage section definitions; no accounts or business copy. V3 creates the corporate route identity index. V4 enables RLS and revokes anon/authenticated table grants only on the 17 application tables. No DROP/TRUNCATE operations; stable migrations are unchanged. Security boundary changes in V4 are intentional. Backend database access must use an authorized role; frontend has no Supabase SDK/key.

## Actual verification

- Backend command: `bash scripts/test-backend.sh`; 62 tests passed (7 security unit, 13 mail configuration/provider, 42 PostgreSQL integration), zero failures/errors/skips; Spotless check and executable jar build passed. Tests use disposable PostgreSQL and file/mock mail; no real Gmail sends.
- Initial Supabase preflight: three attempts returned SQLState **28P01**. After a subsequent user password correction, read-only preflight connected successfully and found no application tables. The old Docker-backed backend was stopped.
- Supabase runtime: Flyway applied V1–V4; postflight verified **17/17 core tables, 4 successful migrations, RLS and BYTEA**. JPA `ddl-auto=validate` passed. The second backend startup validated all four migrations and reported schema v4 up to date with no migration necessary.
- TLS: `sslmode=require` successfully enforces the JDBC client-to-session-pooler TLS connection. `pg_stat_ssl` reports **false for the pooler's PostgreSQL backend connection**. These are separate connection legs; the result is not an end-to-end TLS guarantee. Review the provider's upstream connection settings before production; no SSL configuration was weakened.
- On the user's later explicit request, the first Supabase SUPER_ADMIN was bootstrapped with a freshly generated random password, not Docker QA credentials. Real API and browser login verified the role and mandatory MFA gate; dashboard before MFA returned 403. One-time BOOTSTRAP_ADMIN values were cleared before restart. Private credentials are in ignored `.local/supabase-admin.json` (0600). Owner Authenticator enrollment remains for the user; no MFA secret was generated by the agent.
- Gmail SMTP live connectivity: `bash .local/check-smtp.sh` passed TCP/STARTTLS/hostname verification and SMTP authentication using local env credentials. This ignored manual probe sends no email. Real OTP send and inbox delivery are not yet verified.
- Frontend application/UI source is unchanged. Playwright configuration gained the target guard; `npm run lint`, `npm run typecheck`, `npm run test` (13 passed) and `npm run build` passed. `npm run test:e2e -- --list` was deliberately refused by the guard under the configured Supabase/smtp target; no browser journey or mail send was run.

Security check: configured database/Gmail passwords and security keys have zero exact matches in tracked files, current diff or Git-history blobs. `.env` and `backend/.env` are untracked and ignored; no commit was created. Diagnostic output never displayed secret values. The manual SMTP probe is also ignored and contains no credentials.

## Admin CMS code/API audit

| Existing screen/domain | Backend authorization and behavior reviewed |
| --- | --- |
| Dashboard | Policy admin: EDITOR content scope; ADMIN/SUPER_ADMIN require verified MFA |
| Posts / Categories / Pages | Content-kind guard allows EDITOR only POST/PAGE/CATEGORY; draft/publish/archive and bilingual DTOs remain |
| Media | Admin policy; private file access authenticated; public visibility and reference guards remain |
| Branches / Products / Partners / Certifications / Hero | Content-kind guard requires ADMIN/SUPER_ADMIN with MFA |
| Homepage | Business policy; fixed sections and validated published references remain |
| Contact Messages | Business policy; bounded listing and status updates remain |
| Users | Business policy; ADMIN cannot manage privileged targets or invite privileged roles |
| Roles / Audit Logs | SUPER_ADMIN + verified MFA |
| Settings | SUPER_ADMIN; updates also require recent authentication |

Policy rejects USER; mixed privileged roles cannot bypass MFA through EDITOR. BearerFilter verifies live sessions/account state/roles. Role/status changes revoke sessions; last active SUPER_ADMIN is protected under an advisory transaction lock. Private/draft content is filtered on public APIs. Existing regression suite covers these boundaries. This is code/API review plus disposable-PostgreSQL regression, **not yet a privileged CMS runtime audit against Supabase**. That requires the user's own bootstrap configuration and MFA, and will not create fake business data.

## Separate local frontends

Public: `npm run dev`, port **5173**. Admin: `npm run dev:admin`, port **5180**; 5174/5175 were occupied by Docker. Vite mode selects public versus admin routes; root/admin login and customer links resolve the correct origin. Public `/admin/*` redirects to the admin origin; admin does not show registration or corporate navigation. Backend CORS includes both origins, security policies unchanged. Build outputs are dist and dist-admin. Same-host cookies can be shared across ports; this is UI/origin separation, not independent session stores.

Verification after this change: frontend lint/typecheck, **16 Vitest tests**, public and admin production builds passed. Private-browser smoke checks verified both origins, anonymous redirects and real Supabase admin login → mandatory MFA setup → logout. No auth trace/screenshot, inbox access, business fixtures or live OTP send were used. The backend code is unchanged from the successful 62-test run.
