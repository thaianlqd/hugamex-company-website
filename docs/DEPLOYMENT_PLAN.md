# Production plan — no deployment performed

1. Approve the factual content, photos, contact details, privacy/retention policy, partner brand rights and current certificate documents. Archive all QA fixtures; replace stock imagery. Review language translations and canonical URL policy.
2. Create an isolated staging Supabase database. Supply JDBC connection details with SSL, choose transaction/session/direct connection mode for Flyway/JDBC, and provision separate migration and runtime roles. Flyway needs DDL rights; the backend needs only the app-table privileges plus an explicit RLS access strategy. Never use `anon`/`authenticated` for JDBC or put DB/service keys in frontend variables. Disable unnecessary Data API exposure, verify role grants and RLS after migrations.
3. Generate four independent 32-byte Base64 keys in a secret manager. Define backup and rotation procedures, especially retaining the MFA decryption key. Choose a domain and exact HTTPS CORS/FRONTEND_URL/VITE_SITE_URL. Use `SPRING_PROFILES_ACTIVE=prod`; never enable dev mail or Swagger publicly.
4. Configure Google OAuth web credentials, exact backend callback URI ending `/login/oauth2/code/google`, consent screen and authorized domain. Exercise state/PKCE, rejected unverified email, account conflict, failure redirect, disabled account and privileged-user MFA on staging. No automatic account linking is enabled.
5. Configure authenticated TLS SMTP, sender identity and delivery settings. Test email OTP expiry/resend/invalid attempts and password reset delivery with an authorized test mailbox. Review SPF/DKIM/DMARC with the mail operator; live mail has not been enabled by this project.
6. Build frontend and backend using the documented checks. Serve frontend dist behind HTTPS with SPA fallback. Route `/api/`, `/oauth2/` and `/login/oauth2/` to Spring; route `/sitemap.xml` to `/api/v1/public/sitemap.xml`. Restrict backend and DB network exposure.
7. Apply reverse-proxy headers to HTML/static frontend responses. Start with CSP `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://images.pexels.com; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`. Blob images are needed for authenticated CMS previews. React/Motion currently use style attributes; review tighter style policies with actual build. JSON-LD needs an explicit nonce/hash strategy if a strict CSP blocks it. Remove Pexels once photos are replaced. Add approved API origin to connect-src only if using separate origins. Add nosniff, Referrer-Policy, Permissions-Policy and HSTS after HTTPS validation. This is a starting policy, not a tested production configuration.
8. Run all unit/PostgreSQL/browser/a11y checks against staging. Verify Secure/HttpOnly/SameSite cookie paths, OAuth redirects, uploaded media, 404/SPA behavior, robots/indexing, sitemap/canonical host, proxy client IP and security headers. Test DB backup restore and MFA-key recovery. Run Java SCA and an independent security review; reassess the Spring 3.x patch/support strategy and DPoP advisory applicability before enabling any new auth flow.
9. Bootstrap an owner-controlled SUPER_ADMIN once with a unique passphrase; remove bootstrap variables immediately; enroll MFA and retain recovery codes securely. Create an additional authorized SUPER_ADMIN for organizational recovery, then EDITOR/ADMIN accounts with appropriate least privilege. Do not migrate local QA accounts or secrets.
10. Define monitoring, encrypted backups, restricted logs, DB growth alerts for BYTEA, expired challenge/session/rate bucket retention and client-approved contact retention. Schedule media malware scanning if upload threat model requires it. Run realistic media/traffic load tests.
11. Review the concrete staging result with the site owner. Production publishing, DNS changes and production migrations require explicit instruction in a later task. No such actions have been taken.

SPA metadata is client-rendered. Google can render JavaScript, but non-JavaScript social preview bots may need prerender/SSR if rich sharing previews are a launch requirement. VI routes are canonical for both languages; a separate indexed English URL strategy remains a product choice before launch.
